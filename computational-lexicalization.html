Computational Lexicalization

Turning design knowledge into callable language.

Computational Lexicalization proposes a way to make design knowledge legible to people and executable by machines. The research responds to a persistent gap in computational design: designers work through intention, judgment, and iterative exploration, while parametric tools require explicit instructions and formal logic.

Authors

01 · The cognitive gulf

Syntax without meaning, meaning without syntax

Parametric tools speak syntax: precise rules and generative logic for how form is made, increasingly detached from the intuitive, ambiguous way designers actually think. Large language models bring semantics: they understand what is wanted and why, but lack the precision, editability, and structural logic of a grammar. Computational lexicalization bridges the gulf by restructuring design knowledge into a language that is both human-readable and machine-executable.

Across the cognitive gap

02 · Lexicon and grammar

Minimal dual units, two-level grammar

Each entry in the lexicon is a minimal dual unit: a computational instruction paired with a semantic tag — generate_facade_elements is at once a Grasshopper operation and a phrase a language model understands. Grammar splits into two levels: a high-level semantic grammar run by the LLM — task scheduling, data connection, tool calling — and a low-level geometric grammar run by parametric tools — precise execution, parameter computation, geometry generation.

03 · Why symbolic generation

Instructions, not sculpture

Generative AI reaches 3D by three paths: voxels, meshes and splats, or symbols. The first two output frozen geometry — visually striking digital sculpture that resists editing, carries no build logic, and does not survive BIM. The symbolic path has the model write sequences of modeling instructions instead of geometry itself: the output stays editable, lightweight, and legible as a design process, and the designer can step in at any point along the way.

04 · The design agent

A reason–act loop over MCP

An LLM-centred agent interprets intent, plans steps, calls tools, evaluates results, and corrects itself. The Model Context Protocol connects it to Grasshopper through an open-source component: CategoryFilter limits which component categories the agent may touch, and SetParameterMode sets how much it is allowed to change — the designer draws the agent's behavior space before it acts.

The Grasshopper MCP component

05 · Bounded autonomy

Three tiers of agent freedom

Level 1 treats the agent as a natural-language interface that tunes parameters in a designer-built definition. Level 2 — the framework's core working mode — lets the agent select, tune, and compose operations within a designer-defined lexicon: rules first, creation inside them. Level 3 frees the agent to assemble base components on its own, trading design rationality for the widest creative space.

Designer-led → agent-led

06 · Tested in the field

One framework, many vocabularies

The framework was validated at the DigitalFUTURES 2025 Landscape Agent workshop, where teams encapsulated landform, planting, zoning, and public-space knowledge into lexicon libraries of their own and ran them through the agent. Most teams settled into Level 2 on their own, and the granularity of encapsulation proved to be a design decision in itself. The workshop and its outcomes live on the Landscape Agent page.
